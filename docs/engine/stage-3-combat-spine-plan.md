_Handoff-ready build plan for Stage 3 of the v12 critical path: make combat a first-class, multi-round mode on the parallel `PipelineActionStateMachine` — an engine-owned combat spine (contested roll + severity bands, `combatState` as scene-state, a once-per-day no-one-shot floor, a lifted round cap) plus the combat prompt rules and an offline sim proof. Pipeline-only; the live v11 path stays frozen. Executed in two passes: **Pass 1 (this orchestration) = the pure foundations (T1 band math + T2 combatState model), then a human checkpoint**; Pass 2 = the round loop, templates, and sim proof. Every anchor, type contract, and settled decision is inlined so a lesser agent can execute task by task._

---

## Why this shape

Stage 1 split the mega-call into classify → decide → (dice) → resolve on a parallel machine; Stage 2 pinned the typed, graph-shaped scene-state spine (`relations` table, `set_relation`/`update_relation`, endpoint resolution). Stage 3 is the first *heavy writer* of that spine: combat ([[prompt-v12-combat]]). Combat today is a generic `/action` roll pushed to end in 2–3 beats — backwards for a survival game where the wilds should host frequent, long, richly-rewarded fights ([[mvp-combat]]). The rich version (bounded severity bands, a boar that *stays* near death, a no-one-shot floor) can't be done with prompt rules alone: the engine has no enemy — `modify_health` hits only the player, and nothing tracks a foe across rounds. Stage 3 adds the engine-owned combat spine and models the enemy as an `in_combat` scene-state edge (the first per-`relType` prop schema Stage 2 deferred to "its writers").

## Settled decisions (ratified — do not re-litigate)

1. **Pipeline-only. The live v11 path stays frozen.** Everything lands on `PipelineActionStateMachine` / the pipeline contracts / new additive pure modules. No change to `machine.ts`, the live `PROMPT_VERSION` (`v11`), or prod `startAction`/`applyResolution` behaviour. Combat reaches players when the pipeline is later promoted, not in this stage. (Confirmed with the human across Stages 1–2.)
2. **Two-pass execution with a checkpoint.** Pass 1 = T1 (band math, pure `dc.ts` extension) + T2 (combatState model + per-`relType` prop schemas, pure) — purely additive, touches nothing that runs today, fully unit-testable in isolation. **Human review, then** Pass 2 = T3 (round loop + floor in the machine) + T4 (combat templates) + T5 (per-round logging + sim combat scenario + metrics). This doc specs all five so Pass 2 is anchored; only T1–T2 execute now.
3. **The engine owns the enemy's numbers; the LLM owns identity + narration.** `enemyHp`, `enemyMaxHp`, `round`, and the band→damage deltas are engine-authored and deterministic (bounded, tune-able). The LLM (resolve stage) supplies the enemy's *name* and *endpoint type* and *narrates* the band the engine already decided — it never authors `enemyHp` or the core damage. This preserves the [[prompt-v12-combat]] "engine owns `enemyHp`, the LLM only narrates it" invariant and keeps the distribution bounded (no LLM-authored one-shots).
4. **Hybrid enemy anchoring (human-ratified).** The `in_combat` edge points at an **npc node** when the foe is a **named NPC or boss** (`pc → in_combat → npc`, resolved against nearby NPCs like any relation); it points at the **current location** for **unnamed minions/wildlife** (`pc → in_combat → location`, resolves by name with no lookup, no npc row minted). The resolve stage authors the endpoint type; the combatState helper reads whichever edge exists. POC scope: one active enemy edge per (pc, anchor); multiple simultaneous distinct enemies at one location collide on the unique key and are **out of scope** (deferred to a co-op/boss stage). Rationale: minions are cheap and place-anchored ("the wounded boar is still in the clearing"); named foes deserve a persistent node.
5. **The no-one-shot floor is true per-day (human-ratified).** A blow that would drop the player to ≤0 HP instead leaves them at **1 HP + a forced desperate choice**, gated **once per in-game day** via a persistent `pc → combat_save{savedDay} → pc` self-edge: the save fires iff `savedDay !== currentDay`. Requires threading `currentDay` into the resolve `mutationCtx` (a resolver method mirroring `getKnownLocations`). Once the save is spent for the day, a would-be-lethal blow lands (HP floors at 0 via the existing clamp). **Death consequence itself is greenfield and out of scope** — no death mechanic exists today (`metrics.ts:11-15` hardcodes `death: null`); Stage 3 makes HP=0 observable (trace marker), not fatal. The floor mechanic (save-once-per-day, then unprotected) is the deliverable.
6. **Contested roll, engine-side enemy die.** Each combat round the player rolls the existing `d20 + abilityCheckBonus` (`dc.ts`, unchanged) **and the engine rolls an enemy `d20`** from the SAME injectable `rollD20` (so the sim's seeded/sequence source stays fully deterministic — a combat round consumes **two** draws). The signed margin `playerTotal − enemyTotal` maps to a severity band. "Contested" therefore adds no LLM randomness (decision 3).
7. **Scale magnitude, not variance; no world-tier dependency yet.** The band set, thresholds, no-one-shot floor, and the distribution *shape* are global constants. Thread B (World Tier) does not exist (`grep` confirms: no `worldTier`/reward-scaling in `src/`) — Stage 3 must **not** depend on it. The band→damage table and `enemyMaxHp` derivation are engine constants derived from the encounter's existing `baseDc`; Thread B (Stage 4) later reaches only `enemyMaxHp` + the band-damage magnitudes through a seam T1/T2 leave open (a `scale` factor defaulting to 1).

## Grounding facts (verified against the code — anchors for the executor)

- **Verdict is binary.** `dc.ts:resolveRoll(d20, bonus, dc): 'success'|'failure'` (`dc.ts:66-74`) — nat-1 always fails, nat-20 always succeeds, else `d20+bonus >= dc`. There is **no** crit/margin verdict object; the pipeline threads the raw `d20Roll` into resolve (`PipelineActionStateMachine.ts:273, 288-294`). Combat's band math is **new** and layered on top — it does not change `resolveRoll`.
- **No enemy HP, no combat state, no death, no floor exist today.** `modify_health` targets the player only (`mutations.ts:223-235, 387-390`; `WorldEngineImpl.ts:1395-1398` clamps `[0, maxHealth]`). `enemyHp` appears only in *comments* as a future relation-prop example (`mutations.ts:32`, `relation.ts:60`). No `savedToday`/survive-at-1 anywhere.
- **Relations spine (Stage 2) is ready.** `set_relation`/`update_relation` validated at `mutations.ts:333-347`; `RELATION_TYPE_WHITELIST = {in_combat, trust, disposition, knows_secret, fears, owes_debt, puzzle}` at `mutations.ts:34-42` (extensible — writers add theirs); `RELATION_NUM_CLAMP = 9999` (`mutations.ts:46`); per-`relType` prop schemas explicitly deferred to "their writers" (`mutations.ts:31-33`) — **that is this stage**. `applyMutations` collects edges into `AppliedState.relationsToSet`/`relationsToUpdate` as-authored (`mutations.ts:450-454`). `RelationRepository.updateProps` already sums numeric props as deltas (`relation.ts:60-90`) — ideal for `enemyHp -= n`.
- **Endpoint resolution (Stage 2 T3).** `resolveAuthoredRelation(relation, char, nearbyNpcs): RelationKey | null` (`relation-wiring.ts:61-77`) — npc by case-insensitive nearby match (drop-with-warn if unresolved), location name-keyed, pc → `char.id`. combatState read-back flows through `buildPipelineContext` → `resolver.getSceneRelations({type:'pc', ref})` → `LlmContext.sceneState: SceneStateEdge[]` (`pipeline-context.ts:71-77`, `LlmGateway.ts:50, 57-62`).
- **The machine's injection seams.** The pipeline `resolve()` already injects mutations deterministically around the LLM stages: the travel gate between resolve-mutate and finalize (`PipelineActionStateMachine.ts:299-303`) and the wage append post-finalize (`:333-335`). Combat's engine-authored damage mutations follow the **same pattern** — injected by the machine, not authored by the LLM.
- **Beat cap.** `MAX_DECISIONS_PER_ACTION = 2` (`prompt-builder.ts:21`); the pipeline caps at `state.decisions.length >= MAX_DECISIONS_PER_ACTION - 1` (`PipelineActionStateMachine.ts:210`). Combat needs a **higher, sub-mode-gated** cap (decision below).
- **Sim harness.** `PipelineScriptedGateway` scripts each stage (`classify`/`decide`/`resolveMutate`/`resolveNarrate`, `src/sim/PipelineScriptedGateway.ts`); multi-beat keyed off `input.context.previousDecisions.length` (`types.ts:55-61`), NOT `callNo`. Seeded dice via `makeRollD20` with `{kind:'sequence',values[]}` (`roll-source.ts:22-40`) — a combat round consumes two draws (decision 6). `PipelineSimEngine` owns the seeded `:memory:` world + `RelationRepository` and injects `createGeographyFinalize` as the machine's finalize (`PipelineSimEngine.ts:99-104`); `getPersistedRelationCount` exposes `relationRepo.count()` (`:200-202`). `SimResult { turns, stageCalls?, relationsPersisted? }` (`types.ts:174-187`). `currentDayNumber(engine)` (`driver.ts:183`) is the day source for decision 5.

## Combat spine — the model

### combatState (the `in_combat` edge)

```
pc ──in_combat{ enemyName, enemyHp, enemyMaxHp, round }──▶ npc        (named foe / boss — decision 4)
pc ──in_combat{ enemyName, enemyHp, enemyMaxHp, round }──▶ location   (minion / wildlife — decision 4)
pc ──combat_save{ savedDay }──▶ pc                                    (the once-per-day floor — decision 5)
```

- **Props (engine-owned numbers, decision 3):** `enemyName: string` (LLM-supplied identity), `enemyHp: number` and `enemyMaxHp: number` (engine-derived), `round: number` (engine-incremented, 1-based). Per-`relType` clamp: `0 ≤ enemyHp ≤ enemyMaxHp`, `1 ≤ enemyMaxHp ≤ ENEMY_HP_MAX` (see T2 constants), `round ≥ 1`.
- **`enemyMaxHp` derivation (no world tier):** `enemyMaxHp = clamp(round-ish(baseDc), ENEMY_HP_MIN, ENEMY_HP_MAX)` with a `scale` seam (default 1) Thread B later multiplies. Concrete starting rule: `enemyMaxHp = clamp(Math.round(baseDc * scale), 6, 20)`. **Sim-tunable** (T5) — a starting value, not final balance.

### Contested roll + severity bands (decision 6)

- `playerTotal = playerD20 + abilityCheckBonus(char.stats, items, rollStat)` (existing).
- `enemyBonus = clamp(baseDc - 10, 0, ENEMY_BONUS_MAX)` — the encounter DC *is* the foe's strength (no tier). `enemyTotal = enemyD20 + enemyBonus`.
- `margin = playerTotal − enemyTotal`. Band table (magnitudes carry a `scale` seam, default 1; **starting values, sim-tunable**):

| Band | Margin `m` | `enemyHp` Δ | player HP Δ | Feel |
| ---- | ---------- | ----------- | ---------- | ---- |
| `clean` | `m ≥ +8` | `-6` | `0` | you dominate the exchange |
| `glanced` | `+2 ≤ m < +8` | `-3` | `0` | you edge it |
| `trade` | `-2 ≤ m < +2` | `-2` | `-2` | blows are exchanged |
| `heavy` | `m < -2` | `-1` | `-3` | the foe dominates |

- **Crits swing the band, consequence stays bounded:** player nat-20 → force `clean` and amplify `enemyHp` Δ by `-2`; player nat-1 → force `heavy` and amplify player HP Δ by `-2`. Enemy nat-20 → force `heavy`; enemy nat-1 → force `clean` (symmetric, still band-bounded, no extra amplification — the opposing player crit already covers the "extra" case). Amplification never exceeds the band's own cap by more than the fixed crit bonus (bounded — decision 7). **Precedence when both dice crit and disagree** (settled — T1 review): the player's own die always wins the band, so player crits are evaluated before enemy crits (a player nat-1 opposite an enemy nat-1 resolves to `heavy` + amplified, not `clean`). Amplification never stacks — a single crit contributes at most one `-2`.
- Player HP Δ passes through the existing `modify_health` path (validator + `collapseStackedDeltas` `HEALTH_DELTA_CAP = -4`, `mutations.ts:110-111` — all starting deltas are within cap). `enemyHp` Δ is an `update_relation` prop delta (summed by `relation.ts:60-63`), *not* subject to the health cap.

### Round loop + termination (decision on the cap)

- **Lifted cap:** combat sub-mode caps at **`MAX_COMBAT_ROUNDS = 4` rounds after the initiating decision** (≤6 total when a non-combat decision leads in). Non-combat actions keep `MAX_DECISIONS_PER_ACTION = 2`. Sub-mode = `actionType === 'combat' && required && combatState present`.
- **Termination, checked each round after applying the band:**
  1. `enemyHp ≤ 0` → **win** → resolve `success` (loot/reward via the combat success template; enemyHp clamped at 0); clear/settle the `in_combat` edge.
  2. player HP would go `≤ 0` → **floor** (decision 5): if not saved today → clamp to 1, set `combat_save.savedDay = currentDay`, emit a **forced desperate choice** beat (options: `bail bloodied` / `last stand`); if already saved today → HP floors at 0, resolve `failure` with a `hp_zero` trace marker.
  3. player **bail** → existing bail path (`PipelineActionStateMachine.ts:166-191`, `-BAIL_STAMINA_COST` stamina), enemy edge left persisted at current `enemyHp` (remembered — decision 4).
  4. round `> MAX_COMBAT_ROUNDS` → **derive** winner from remaining HP fraction: `playerHp/maxHp ≥ enemyHp/enemyMaxHp` → `success` else `failure`.
- Otherwise increment `round`, author the `update_relation` (enemyHp Δ + round), and continue to the next decide beat.

### Task 3 — Combat round loop + no-one-shot floor in the machine · **Pass 2**
**Description.** Wire the spine into `PipelineActionStateMachine` (pipeline-only; `machine.ts` frozen): the lifted combat cap, the per-round contested roll + band application, engine-authored enemyHp/player-HP mutations injected around resolve (mirroring the travel-gate/wage injection pattern, `:299-303, 333-335`), combatState establishment/read/update, the once-per-day floor + forced desperate choice, and the termination ladder. Thread `currentDay` into `mutationCtx` via a new optional `PipelineContextResolver.getCurrentDay?(): number` (mirroring `getKnownLocations`), wired in `PipelineSimEngine` to `currentDayNumber`. **Exit:** a scripted combat action runs multiple rounds, enemyHp persists + depletes across beats, a win/floor/cap each resolve correctly, and the floor fires at most once per day. **Files:** `PipelineActionStateMachine.ts`, `src/engine/action/pipeline-context.ts` (resolver type + `getCurrentDay`), `PipelineSimEngine.ts` (wire day + establish/read combat edges), tests. **Deps:** T1, T2. **Scope:** XL — the executor should land it in reviewable sub-steps (cap+sub-mode → round band application → floor/save → termination ladder).

**T2 carry-forward for T3 (npc-anchor round-trip — flagged in T2 review):** `SceneStateEdge.to.ref` for an `npc` anchor is the resolved numeric npc **id** (`relation-wiring.ts`), but `RelationEndpoint.npc` carries a **name** for `resolveAuthoredRelation`'s case-insensitive `nearbyNpcs` match. So `readCombatState`'s `anchor` for an npc fight is an id-as-name and would **not** re-resolve if fed back through `resolveAuthoredRelation`. T3 must, for an npc-anchored fight, **resolve the npc endpoint once and hold the resolved `RelationKey` across rounds** (skip re-resolution), or thread the npc's name through separately — do not round-trip an npc anchor via `AuthoredRelation`. Location anchors (minions) round-trip cleanly and need none of this.

**T3 design — settled (Pass 2, ready to execute).** The plan above fixes intent; these are the implementation-level decisions the lead settled after reading the machine + T1/T2 + sim wiring, so the executor does not guess. None overturn a ratified decision; they resolve the gaps the plan delegated ("executor's call", "T3 must…"). Mirrors the "As built (T2, ratified)" style used for T2 above.

1. **Combat rounds are decision beats.** Each `step()` in combat sub-mode is one round: the player picks an approach option, the engine rolls the contested pair, applies the band, then either terminates (win/loss/cap) or presents the next round's decide beat. Sub-mode gate: `state.actionType === 'combat' && state.required` (combat is reactive/required, T4 rule). Non-combat actions keep `MAX_DECISIONS_PER_ACTION`. The combat handler short-circuits `step()`'s generic beat-cap/decide/resolve flow.
2. **Per-round mutation persistence (the architectural gap the round-loop bullets gloss).** Today the machine emits/persists mutations only at the terminal `resolve()`; combat needs `enemyHp` + player HP to persist on *non-terminal* beats. Settled: the machine-internal `PipelineStepResult` non-resolved variant carries an optional `mutations?: WorldMutation[]`, and `PipelineSimEngine` applies + persists them each beat via a shared apply path (extracted from `applyOutcome`). The public `ActionStepResult` (`WorldEngine.ts`) stays unchanged, so the live v11 path is untouched (decision 1).
3. **Enemy identity + anchor ride on DECIDE, not resolve.** Establishment happens on the first combat beat and only DECIDE runs on non-terminal beats, so the signal cannot come from the resolve stage. Add an optional `PipelineDecideResult.combatEnemy?: { name: string; anchor: 'npc' | 'location' }`. Absent, or an `npc` anchor that fails to resolve against `nearbyNpcs`, defaults to a **location-anchored minion** named generically (decision 4 fallback, so combat always establishes). This reconciles decision 3's "resolve supplies the name" wording: for POC, the identity channel is DECIDE because that is the only LLM stage that runs before establishment.
4. **Hold the authored anchor across rounds (resolves the T2 npc caveat for both anchor kinds).** The machine holds the authored `RelationEndpoint` in `PipelineInternalActionState.combatAnchor` from establishment and emits every round's `set_relation` against it, never re-deriving the anchor from `readCombatState` (whose npc `anchor` is the id-as-name that would not re-resolve). `readCombatState` supplies only `enemyName`/`enemyHp`/`enemyMaxHp`/`round`. Location anchor = `{ node: 'location', name: char.location }`.
5. **Active-combat test + dead-edge handling (no `delete_relation` op exists).** A win leaves the edge at `enemyHp = 0` (the vocabulary has no delete op). Establishment treats "`combatState` present AND `enemyHp > 0`" as active; a `<= 0`/absent edge establishes fresh (a new `set_relation` overwrites the dead edge on the same unique key), so the lingering dead edge is harmless. A real edge-clear awaits a `delete_relation` op (out of scope; note it for a later stage).
6. **Combat resolve skips the dice path.** The round's contested roll already decides the verdict, so termination resolves with a pre-determined verdict (win / derive-win → `success`; loss / derive-loss → `failure`) and does **not** call `resolveRoll`. `resolveMutate` still runs for ancillary loot only (decision 3, never `enemyHp`/core damage); the engine-authored final-round mutations (player HP Δ + `enemyHp`) are injected into the outcome ahead of the loot. `playerRolled` reports the round's `playerD20`.
7. **enemyBonus + enemyMaxHp source.** Both derive from the encounter's raw `baseDc` on `state.lastDecideResult.baseDc` (not `accumulatedDc`, which drifts once dcModifiers accumulate): `enemyBonus = clamp(baseDc - 10, 0, ENEMY_BONUS_MAX)`, `enemyMaxHp = deriveEnemyMaxHp(baseDc)`, `scale` stays 1 (decision 7). Player bonus = `abilityCheckBonus(char.stats, items, chosenStat)`.
8. **Round numbering + cap.** Establishment sets `round = 1`; each combat step fights the current round then persists `nextRound = round + 1`. `MAX_COMBAT_ROUNDS = 4` fought rounds after initiating; on the beat where the current round would exceed the cap, derive the winner from the HP fraction (decision-6 ladder) rather than fighting another round.
9. **`getCurrentDay` in the sim.** `PipelineContextResolver.getCurrentDay?(): number` mirrors `getKnownLocations`; `PipelineSimEngine` wires it to a locally-held day counter (default 1, settable), matching the driver's existing "day is a locally counted sequence" note (`currentDayNumber` reads a `WorldEngineImpl` meta row the in-memory adapter has none of). Absent → the floor degrades to per-encounter (documented, risk table).
10. **Additive `ActionOutcome` field.** The `hp_zero` marker (iteration 2) is a new *optional* field on `ActionOutcome` (legacy never sets it, mirroring `isDivineIntervention`). Richer per-round beat logging is T5, not T3.
11. **npc-anchor scope for T3.** The sim has no npc store (`getNearbyNpcs` returns `[]`), so an npc-anchored fight cannot persist/round-trip in the sim; only location minions are sim-exercised. The npc-anchor establishment + held-anchor path is covered by machine unit tests with an injected resolver that returns a nearby npc. Full npc-fight persistence awaits an npc-backed sim (later).

**T3 iteration split (two atomic commits, per the "reviewable sub-steps" note):**
- **Iteration 1 — round-loop core:** contract additions (2, 3), `getCurrentDay` (9), establishment (3, 4, 5, 7), contested roll + band application (6, 7), per-beat persistence (2), win + cap-derive termination (6, 8). Player HP clamps at 0 via `applyMutations`; the survive-at-1 floor is deferred to iteration 2 (iteration-1 tests use a high-HP char so HP never reaches 0). Exit: a scripted/unit multi-round fight where `enemyHp` depletes + persists across beats, and win + cap-derive each resolve correctly.
- **Iteration 2 — floor + loss ladder:** once-per-day survive-at-1 via `combat_save` + `getCurrentDay`; the engine-authored **forced desperate-choice beat** (`bail bloodied` routes to the existing bail path with the edge left persisted; `last stand` continues to the next round); the `hp_zero` marker (10) on a second would-be-lethal blow the same day; loss termination (player HP `<= 0` after the save is spent → resolve `failure`).
